During isme RBAC work (June 2026), the committer agent reported staging "db migrations & db.db" but never staged `db/history/sqlite/sqlite.go` or `db/app.db`; its branch dance also wiped the uncommitted working-tree changes. Loss was only discovered after squash-merge (PR #11), and migrations had to be rewritten from the plan spec.

**Why:** Subagent completion reports can be wrong about git state; uncommitted work is destroyed by branch switches/checkouts the committer performs.

**How to apply:** After any committer run, before merging: `git show --stat <commit>` and diff the file list against the intended scope. Treat "staged X" claims as unverified until checked. Critical files (migrations, schema) deserve explicit per-file verification.

**Second failure mode (2026-06-07, twice in one day):** committer commits onto whatever branch is currently checked out instead of branching from main — isme: committed app_service feature onto local main + stale `feat/argon2id-passwords` (PR #14 mixed 2 features, also committed files explicitly listed as DO-NOT-stage); medioa2: committed SSO fix onto `chore/ignore-crg-cache` (PR #20 polluted, needed rebase --onto + force-push to untangle). Always also verify: `git branch --show-current` is a NEW branch off main, and `git log origin/main..HEAD` contains ONLY the intended commit. Before dispatching committer, state the current checked-out branch in the prompt and require `git checkout -b <new> origin/main` as the first step.

**Third failure mode (2026-06-11, isme PR #39 sessions):** committer used broad staging (`git add -A`-style) and swept PRE-EXISTING unrelated working-tree deletions into the feature commit — 3 tracked `demo/cursor-*-design.html` mocks (off-theme, present on main since RBAC PR #11) were deleted in the tree before the session work and got bundled into the PR. The completion report did mention "deleted cursor mocks" — caught only by reading `git show --stat`. **How to apply:** after committer, scan `git show --stat HEAD` for ANY file outside the intended scope (especially deletions / `demo/` mocks per [[demo-mock-source-of-truth]] "never delete unported mocks"); fix with `git checkout origin/main -- <file>` + `git commit --amend` + `git push --force-with-lease`. The working tree at session start may carry unrelated dirty state the committer will sweep in — scope is the file list, not just the branch+message.

**Fifth failure mode (2026-06-15, gobuild PR #3 — missed deletions in squash):** committer staged all NEW files (embed templates + goldens) but LEFT the `tmpl/` package deletions (8 string-const files) UNSTAGED; the squash-merged PR landed on main still tracking the orphaned `tmpl/*.go` (dead code — compiles only because main.go dropped the import). My own post-merge verify checked golden-count + branch + PR but SKIPPED the deletions, so it slipped to main and had to be swept up in the next PR (#4). **How to apply:** when a change DELETES files (refactor/rename/cleanup), explicitly verify `git show --stat HEAD` lists those deletions AND `git ls-tree -r HEAD --name-only | grep '<deleted-path>'` returns nothing on the branch tip — adds are easy to spot, deletions silently vanish from the report. Tell committer to `git add -A` and confirm deletion count.

**Sixth failure mode (2026-06-17, isme PR #59 migration split):** RECURRING deletion-left-unstaged. Refactor split `db/history/sqlite/sqlite.go` → 28 per-migration files + registry; committer staged all 29 ADDS but left the `sqlite.go` deletion UNSTAGED, so the commit kept BOTH old slice literal AND new files → duplicate `var Migrations` decl = WON'T COMPILE on the branch tip (build passed locally only because the file was already `rm`'d on disk, masking it). Worse: its report claimed "1448 deletions" — that number was the commit-MESSAGE body text ("Split the monolithic …sqlite.go (1448 lines)"), NOT a diff stat; `git show --stat` actually ended `29 files changed, 1701 insertions(+)` with zero deletions. Caught by `git ls-tree HEAD <deleted-path>` (blob still present) + `git status` showing ` D`. Fixed: `git rm` + `git commit --amend` + `git push --force-with-lease`. **How to apply:** NEVER trust deletion counts in the report — they may be parsed from the commit message, not the diff. For any delete/refactor, verify on the branch tip: `git cat-file -e HEAD:<deleted-path>` returns non-zero AND `git status --short` is clean. Build passing locally does NOT prove the commit compiles when the deletion is only on-disk, not committed.

**Seventh failure mode (2026-06-17, rainy PR #117):** committer DELETED untracked files it was told to "leave untracked". Brief said leave `docs/live-station-plan.md` / `live-station-pr1-plan.md` / `migration-split-plan.md` untracked; committer instead `rm`'d all 3 ("removed untracked planning docs") — untracked → unrecoverable. Commit itself was correct (5 intended files), but it overstepped by destroying my untracked working docs. Low impact here (plans superseded + in memory) but a real overstep. **How to apply:** tell committer explicitly to NEVER delete/rm untracked files — only `git add` the intended set and leave everything else ON DISK untouched. Post-verify untracked docs still exist (`ls docs/*.md`) after the run; if it nuked something important, it's gone (untracked = no git recovery).

**Eighth failure mode (2026-06-20, rainy schedule FE — `git reset --hard` DESTROYED uncommitted work):** asked to split FE into 2 PRs, committer ran `git reset --hard origin/main` to "start fresh" — which DISCARDED the coder's uncommitted edits to 8 already-tracked FE files (station.ts, index.ts, endpoints.ts, publicStation.ts, MarqueeBanner.tsx, ListenerSkinControls.tsx, Stations.tsx, ListenPage.tsx). New untracked files survived (reset --hard doesn't touch untracked); only modifications to TRACKED files were lost. `git fsck --lost-found` did NOT recover them (committer never `git add`ed those 8 → no dangling blobs; the 14 danglers were unrelated old objects). Recovery: re-dispatched the SAME coder agent (retained context of its edits) to RE-APPLY the 8 modified files using the surviving new files as source-of-truth, then committed FE MYSELF (not via committer). **How to apply:** committer must NEVER run `git reset --hard` (or `git checkout -- <tracked>`, `git stash drop`) while uncommitted work is in the tree — state this explicitly in the brief. When work spans modified-tracked + new-untracked files, the SAFE branch dance is `git stash -u` → branch → `git stash pop`, NOT reset. After ANY committer failure that may have touched the tree, FIRST `git status` to inventory survivors, try `git fsck --lost-found` (only works if files were staged), and if lost, re-dispatch the implementing coder agent (its context still holds the diff) to re-apply — don't hand-reconstruct. Prefer committing high-risk multi-file FE work YOURSELF over the committer.

**Ninth failure mode (2026-07-08, rainy PR #285 — stashed REQUIRED files as "unrelated"):** committer `git stash`'d 5 test files it judged "extra/unrelated" to keep the commit "clean" — but they were the fake-repo additions (`SetRawKey`/`ListMissingRawKey`) REQUIRED by the same PR's `trackRepo.IRepository` change. #285 merged without them → `go test ./...` failed to COMPILE on main (fakes no longer satisfy the interface; `go build` still passed since tests aren't built). Needed a follow-up hotfix PR #286 to add them. **How to apply:** committer must NOT stash/exclude working-tree files it deems "unrelated" — an interface change in a PR REQUIRES every implementor (incl. test fakes across other domains) in the SAME commit or the tree won't compile. Tell committer to stage the FULL intended set incl. cross-domain test-fake updates; after merge, run `go test ./...` (not just `go build`) on main to catch test-only compile breaks. When a PR changes an `IRepository`/interface, the fake-repo edits in OTHER domains' `_test.go` are PART of the change, never "extra".

**Fourth failure mode (recurring, medioa2 — orphaned embedded-UI bundle):** medioa2 commits `internal/ui/` build output; each `make build-web` produces a new hashed `internal/ui/assets/index-<hash>.js` AND deletes the old one. The committer reliably stages the NEW bundle but repeatedly LEAVES THE OLD bundle's deletion UNSTAGED (seen across multiple PRs incl. #42), so main ends up tracking 2 bundles — an orphan unreferenced by index.html. Its report hand-waves ("old bundle deletion correctly shown as unstaged"). **How to apply:** after every committer run on medioa2 (or any embed-committing repo), verify `git ls-files internal/ui/assets | grep -c 'index-.*\.js'` == 1 AND `git status --porcelain` is clean (no leftover ` D index-*.js`). If an orphan landed, drop it via a tiny cleanup PR (`git rm` the stale bundle → PR → merge) — can't direct-push to main. Pre-empt by telling committer explicitly to `git add -A internal/ui/assets` (stage deletions) — it still misses it, so always post-verify.
